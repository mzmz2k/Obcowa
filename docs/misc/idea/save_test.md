Tauri（Rust）とSvelte構成におけるデータ保存の安全性向上は、「Rust側でのアトミック書き込み（アトミック置換）」と「Svelte側での保存リクエストの制御」を組み合わせることで達成されます。

---

## 1. 保存アプローチの比較とメリット・課題

| 保存アプローチ | メリット（機能する点） | デメリット（課題・トレードオフ） |
| --- | --- | --- |
| **① 直接上書き（Simple Write）** | 実装が最もシンプルで、IPC（プロセス間通信）のオーバーヘッドが最小。 | 書き込み中にアプリクラッシュや停電が起きると、ファイル全体が破損（0バイト化）するリスクがある。 |
| **② アトミック保存（Atomic Write）** | 同一ディレクトリに一時ファイル（`.tmp`）を作成し、書き込み完了後に置換するため、途中で切れても既存ファイルが破壊されない。 | 一時ファイルの削除漏れ対策や、クロスデバイス間での移動制限などファイルシステム固有の考慮が必要。 |
| **③ アトミック＋バックアップ保持** | 置換前に `.bak` などの複製を残すため、事故時や誤操作時にも1歩手前の状態に復元できる。 | ディスク容量の消費（一時的に倍増）と、ファイル管理ロジックの複雑化。 |

---

## 2. 設計レベルでのデータ保護（Rust/Svelteの役割分担）

**Svelte側（UI層）の役割：**

* **デバウンス（Debounce）処理：** キー入力ごとの保存を避け、入力停止から500ms〜1000ms後に保存命令を発行する。
* **Dirty / Saving 状態管理：** 「未保存あり（`isDirty`）」と「保存実行中（`isSaving`）」をフラグ管理し、保存完了前にアプリが閉じられそうになった場合は `tauri::window::CloseRequested` イベントをフックして書き込み完了を待つ。

**Rust側（Backend層）の役割：**

* **アトミック置換の実装：** 一時ファイルへ出力後に `std::fs::File::sync_all()` でOSのディスクキャッシュを物理ストレージへ同期させ、その上で `std::fs::rename()` を実行して一瞬でファイルを置き換える。
* **排他制御（Mutex / Serial Queue）：** 同一ファイルに対する複数回の保存リクエストが非同期で交差し、古いデータで新しいデータを上書きするレースコンディションを防ぐ。

## 4. バグ出し・障害テストのアプローチ

* **クラッシュテスト（強制終了）：**
Rustの保存処理内に一時的なスリープを入れた状態で、書き込み直前に `std::process::exit(1)` やタスクマネージャーからの強制終了を行い、次回起動時に既存ファイルが正常に読み込めるか（破損していないか）確認する。
* **連打・競合テスト（ストレス検証）：**
Svelte側からランダムな文字列を含む保存リクエストを短時間に100回連続で発行し、最終的にディスクに書き込まれたファイルの内容が、Svelte側の最新メモリ状態とハッシュ値レベルで一致するか検証する。
* **ファイルシステム障害テスト：**
読み取り専用フォルダへの保存、ディスク容量満杯時の挙動、外部エディタで同時にファイルを開いている場合のロックエラー時に、UI側に適切にエラーダイアログが出るか確認する。

個人開発のV1.0としては、「レベル2（デバウンス ＋ 一時ファイル経由のアトミック書き込み）」まで実装できていれば、日常利用におけるデータ破損リスクは十分に回避できます。
