# プロジェクトの基本情報とルール

## 技術スタック
- フロントエンド: SvelteKit (Svelte 4/5), TailwindCSS, lucide-svelte, Vitest
- バックエンド: Tauri v2 (Rust)
- DB/認証: なし（ローカルの.md/.txtファイルを直接操作）
- 通信: Tauri IPC (フロントから `invoke` でRustを呼び出す)

## コンセプト
Obsidianを母艦として、プロジェクトごとにワークスペースを構成できるMarkdownエディタ。
ファイル・ワークスペースが消えないこと、Obsidianの管理に干渉しないことを優先する。

## 絶対ルール（AIへの指示）
1. **小さく安全に変更すること**: 依頼された機能以外を勝手に追加・削除しない。
2. **既存の機能を壊さない**: 大きな変更が必要な場合は、コードを書く前にまず理由と影響範囲を提案すること。
3. **テーマ対応**: Tailwindで `bg-gray-700` のような具体的な色指定は禁止。必ず以下のCSS変数を使うこと。
【使用可能なCSS変数一覧】
- `var(--bg-color)` : メイン背景色
- `var(--text-color)` : メイン文字色
- `var(--menu-bg)` : メニューやサイドバーの背景色
- `var(--active-highlight-bg)` : ホバー時や選択時の背景色
- `var(--accent-color)` : ボタンやアイコンのアクセントカラー
- `var(--selection-bg)`：文字を選択したときの背景色
※半透明にしたい場合は `color-mix(in srgb, var(--text-color) 20%, transparent)` のようにすること。
4. **ロジックの分離**: 複雑な文字列処理や計算ロジックはUI（Svelte）に書かず、純粋関数として切り出し、Vitestのテストを書くこと。
5. **ディレクトリのルール**: 今後追加していく機能は、機能単位でfeatures/〇〇（機能名）/のようにフォルダを作り、関連するものをすべて格納する。（依存関係をわかりやすくするため）
7. 型定義は厳密にして、anyは使わない
8. ファイル保存、データ保存関係は多少動作が止まってもいいので、エラー時にきっちり警告を出す
9. 新規にファイルを作る際は、一行目にコメント//でファイルの責務の概要を書く（ファイルマップ自動生成用）
