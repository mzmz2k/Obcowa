# 拡張機能：Obsidian Wikiリンクと独自記法のパース・操作設計

## 概要
Obsidianの Wikiリンク (`[[リンク先]]`) をはじめとする独自記法を、アプリケーションのプレビュー画面で再現するための設計指針。将来的な拡張（ハイライト `==`、タグ `#`、画像埋め込みなど）を見越したアーキテクチャとする。

## 設計方針

### 1. Markdownの事前置換パイプライン（`markdownSetup.ts`）
マークダウンが `Marked.js` に渡される前の段階で、文字列置換によるパイプライン処理を行う。
- **プラグイン方式の採用**: 
  - `applyWikiLinks(text)`
  - `applyHighlights(text)`
  のように機能ごとに純粋関数を分け、順次適用することで単一関数の肥大化を防ぐ。
- **HTML化**: 
  - 置換時は独自のカスタムデータ属性を持ったHTMLタグにする。（例: `<a class="obcowa-wiki-link" data-wiki-target="filename">`）
- **安全性の確保**: 
  - コードブロック内（バッククォート内）の記述は置換対象から除外するよう正規表現を厳格化する。

### 2. UIイベント委譲（Event Delegation）（`previewExtensions.ts`）
プレビューエリアのクリック処理などは、個別のDOM要素に対して `addEventListener` を行わない。
- プレビュー領域のルート要素に対して1つのクリックイベントを設定。
- `event.target` のクラス名（`obcowa-wiki-link` など）を見て処理を振り分ける。
- これにより、プレビュー更新時のイベントの再バインド漏れやメモリリークを防ぎ、他の記法のクリック処理も1箇所で管理可能になる。

### 3. Wikiリンクのビジネスロジックフロー
1. クリックされたWikiリンクの `data-wiki-target`（拡張子なしファイル名）を取得。
2. `treeUtils.ts` の純粋関数を用いて、現在のワークスペースの `VirtualNode` ツリーを再帰探索する。
3. **該当ファイルが 1件 の場合**:
   - そのファイルのフルパスを取得し、エディタで対象ファイルを開く。
4. **該当ファイルが 0件 または 2件以上 の場合**:
   - ダッシュボード（または検索タブ）を開く。
   - `searchState` ストアの検索クエリに対象文字列を代入し、初期状態から「ファイル名検索」が実行された画面を表示する。

##　
markdownSetup.ts のソースコードを確認したところ、すでに Marked.js の extensions 機能を用いて、ハイライト（==）や画像埋め込み（![[画像]]）を綺麗に拡張実装されていることが分かりました。
そのため、私が当初提案した「事前置換パイプラインを自作する」よりも、「既存の Marked extensions の仕組みに乗せて Wikiリンク拡張を追加する」 方が、以下の理由で圧倒的に優れています。
既存のソースコードと書き方の一貫性が保たれる。
Marked.js のパース処理に任せることで、「コードブロック内の Wikiリンクは置換しない」といった安全性が自動的に担保される。
