### 将来の「引用埋め込み（`![[ファイル名]]`）」を見据えた設計


#### 💡 提案するアーキテクチャ：ハイブリッド方式（フロントエンド主導の辞書化）

現在の「フロントエンドがツリー全体を管理している（`VirtualNode`）」という特徴を活かし、複雑なRust側の状態管理（Watcherなど）を避ける、以下の設計を提案します。

1. **検索（全文検索・ファイル名検索）用コマンドの改修（アプローチAベース）**
   フロントからは巨大なツリー（JSON）を送るのではなく、**「検索対象に含めるディレクトリパスのリスト（ルートやライブラリのパス）」**だけを送ります。Rustはそれを受け取って、直接高速にディスクを走査・検索します。
   *※JSONのシリアライズ負荷はこれで消滅します。*

2. **Wikiリンク / 引用埋め込み用の「名前解決マップ」の構築**
   ワークスペースをロードした時やツリーが更新された時に、**フロントエンド（Svelte側）で一瞬で計算できる「ファイル名 → パス」の辞書（Mapオブジェクト）**を作ってStoreに持たせておきます。
   - `{"文字列": "C:/path/to/文字列.md"}` のようなシンプルなマップです。
   - 引用埋め込みやリンククリック時は、Tauriに検索を投げるのではなく、**まずこのフロントの辞書を見ます。**
   - 辞書にパスがあれば、そのパスを使って `invoke('read_file_content', { path })` を呼ぶだけなので、検索のオーバーヘッドがゼロになります。

### 今後の進め方のご相談

上記の方針で進める場合、以下の順番でリファクタリングを行うのが最も安全で、既存の機能を壊しません。

* **ステップ1**: Wikiリンク処理を、「フロントエンド側の辞書（Map）を使ってO(1)でパス解決する」ように変更する。（現状の無駄な `search_files` 呼び出しを排除）
* **ステップ2**: Rustの `search_files` コマンドの引数を `nodes: Vec<VirtualNode>` から `target_dirs: Vec<String>` に変更し、Rust内でファイル走査を行うように改修する。（巨大JSON問題の解消）

この設計と進め方でいかがでしょうか？問題なければ、まず**ステップ1**のフロントエンド側（ストアとWikiリンク処理の改修）のコードをご提案します。
